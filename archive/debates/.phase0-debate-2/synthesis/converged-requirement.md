# 规划收敛结果

---

## 共识点

1. **需求信息不完整**：各方一致同意"计数器应用"的需求定义极度简化，缺乏核心使用场景、目标用户和计数目的等关键信息

2. **垂直场景优先于通用工具**：所有方均认同"通用计数器"市场碎片化、壁垒低，应明确定位为垂直场景工具（运动计数、库存管理等）

3. **验证优先于功能交付**：产品方向应通过真实用户反馈验证，而非在假设基础上构建功能

4. **最小可行实验原则**：Sprint 1 应交付最小功能集，仅验证核心假设所需

5. **技术债务需前瞻规划**：简单技术选型适合探索阶段，但需规划"何时重构"的决策点

6. **游戏化是增强层而非核心层**：无论采用何种创新方向，核心计数功能不应因游戏化机制而增加用户摩擦

---

## 关键分歧

### 分歧 1：需求澄清是否应阻塞开发

| 方 | 观点 |
|----|------|
| 需求重构洞察者 | 需要在开发前明确"数什么、为什么数、谁在用" |
| 工程落地官 | 过度澄清会延误决策窗口，可用原型验证代替 |
| 规划收敛者 | 需要在探索中迭代澄清，而非一次性完成 |

**最终裁决**：Sprint 0 应包含"最小可行市场验证"，而非要求完整需求定义。但必须明确**一个核心场景假设**（如"运动爱好者记录俯卧撑次数"）作为验证起点，而非留白。

---

### 分歧 2：创新方向（游戏化/社交）的优先级

| 方 | 观点 |
|----|------|
| 颠覆式创新官 | "数字生命"和"全球共振"是核心差异化方向 |
| 需求重构洞察者 | Gamification 只能作为激励层，不能成为核心价值 |
| 规划收敛者 | 两条路径（工具型 vs 游戏型）必须二选一，不可并存 |

**最终裁决**：创新方向**后置**到 Sprint 3 之后。理由：(1) 核心假设尚未验证时，增加任何附加价值都是过度投资；(2) "数字生命"的渐进衰减机制和"全球共振"的冷启动问题都是可解的，但解法依赖于对目标用户的准确理解，而这仍是未知数。

---

### 分歧 3：本地存储是否属于 MVP 范畴

| 方 | 观点 |
|----|------|
| 规划收敛者原始版 | Sprint 1 包含"本地存储：刷新后数据不丢失" |
| 工程落地官 | 纯内存版本（0.5天）足以验证核心假设 |
| 质疑者 | MVP 应只验证"用户是否愿意用 App 计数"，数据持久化是次级需求 |

**最终裁决**：本地存储**不包含**在核心 MVP 中。Sprint 1 交付物为"纯内存版本 + 基本约束（无负数、无溢出）"，仅验证"用户是否愿意用 App 完成计数操作"。本地存储在用户反馈"我不想每次重置"后升级。

---

### 分歧 4：技术方案评估维度

| 方 | 观点 |
|----|------|
| 工程落地官 | 技术难度 2/10（Hello World 级别），推荐 HTML+CSS+JS |
| 其他方 | 技术评估未考虑离线能力、数据安全、可扩展性 |

**最终裁决**：维持 Web (HTML+CSS+JS) 作为 Sprint 1 技术选型，但**修正评估结论**：
- 技术难度修正为 **4-5/10**（含基本约束实现）
- 存储方案明确为 **IndexedDB**（优于 LocalStorage，支持更多数据类型）
- 架构演进决策点：在 Sprint 3 前进行架构评审

---

### 分歧 5：商业变现路径适配性

| 方 | 观点 |
|----|------|
| 商业闭环操盘手 | 推荐 Freemium + 订阅制，市场规模 <$500M/年 |
| 质疑者 | Freemium 需要海量用户基数才能盈亏平衡，与小市场矛盾 |

**最终裁决**：变现路径应与市场规模匹配。初期的变现策略调整为：
- **阶段 1（市场验证期）**：不设变现目标，聚焦用户增长
- **阶段 2（产品成熟期）**：采用"一次性付费 + 增值服务"模式，针对垂直场景（如健身计数器的高级训练计划模板）
- **阶段 3（规模化期）**：考虑 B2B SDK 授权

## 收敛需求

### 产品定位

**场景化计数器（Scenario-Specific Counter）**

定位为"特定垂直场景下的专用计数工具"，而非通用工具或习惯养成产品。在目标场景中建立壁垒，提供该场景下最优的交互体验。

**初始验证场景**（待 Sprint 0 确认）：
- 场景 A：运动计数（俯卧撑、深蹲、仰卧起坐）
- 场景 B：库存盘点（仓库、零售、商户）
- 场景 C：会议/活动计数（举手、签到、分组）

### 核心功能（按优先级）

| 优先级 | 功能 | 描述 |
|--------|------|------|
| P0 | 计数增加 | 每次点击 +1，支持步长设置（可配置为 +1/+5/+10） |
| P0 | 计数减少 | 每次点击 -1，不允许低于 0 |
| P0 | 重置 | 一键归零，需确认操作 |
| P0 | 数值显示 | 大字体、高对比度，适配不同光线环境 |
| P1 | 本地持久化 | 单设备数据保存，下次打开保留上次数值 |
| P1 | 音效反馈 | 计数时有短促音效确认（可关闭） |
| P2 | 历史记录 | 最近 N 次操作的本地记录（可导出） |
| P2 | 多计数器 | 支持同时管理多个计数器实例 |

### 创新机制（暂缓，等待市场验证后决策）

| 机制 | 状态 | 触发条件 |
|------|------|----------|
| 数字生命（渐进衰减） | 搁置 | 需先验证用户使用频率是否支撑养成机制 |
| 全球共振 | 搁置 | 需先验证垂直场景的初始用户基数 |
| 游戏化成就系统 | 搁置 | Sprint 2 用户反馈显示留存问题后重新评估 |

## 验收标准

### Sprint 0：市场验证

- [ ] **访谈或问卷**：收集至少 10 个目标场景用户的真实计数痛点
- [ ] **替代方案分析**：记录用户当前使用的替代方案（纸笔、计算器、其他 App）及其具体痛点
- [ ] **场景锁定**：基于访谈结果，明确选择**一个垂直场景**作为产品核心定位
- [ ] **验收决策**：如果存在真实痛点且现有替代方案存在明显不足 → 进入 Sprint 1；否则 → 终止或转向

### Sprint 1：最小可行实验

- [ ] **功能完整性**：用户可在单次会话内完成 +1/-1/重置的完整操作
- [ ] **基本约束**：计数器下限为 0（不可出现负数），上限为 999,999,999
- [ ] **响应速度**：操作响应时间 <100ms
- [ ] **验收决策**：在目标场景用户中，7 日内重复使用率 >30% → 进入 Sprint 2；否则 → 重新评估场景假设

### Sprint 2：功能增强（基于 Sprint 1 反馈）

- [ ] **本地持久化**：数据在 App 重启后保留
- [ ] **步长配置**：用户可自定义每次计数的增量值
- [ ] **历史记录**：支持查看过去 30 天的计数记录
- [ ] **场景适配**：基于用户反馈，调整 UI/UX 以适配目标场景（如大按钮、高对比度）

### Sprint 3：架构评审（触发条件：Sprint 2 验证通过且有明确扩展需求）

- [ ] **技术债务评估**：当前技术栈是否支撑下一阶段功能？
- [ ] **用户同步需求**：是否需要跨设备数据同步？如需要，引入后端架构
- [ ] **安全合规**：如涉及敏感数据（医疗、库存），评估加密存储需求

## 风险与注意事项

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|--------|------|----------|
| **场景选择错误** | 高 | 高 | Sprint 0 强制要求真实用户访谈；避免"猜测用户需求" |
| **MVP 范围蔓延** | 中 | 高 | Sprint 1 仅包含核心功能，任何新增需在 Sprint 2 重新评估 |
| **技术债快速累积** | 中 | 中 | Sprint 3 设置架构评审决策点，不允许无限制地在简单技术上叠加功能 |
| **冷启动无用户** | 高 | 高 | 初期选择已有社群基础的垂直场景（如健身博主社群），而非从零构建用户群 |
| **用户将计数器视为一次性工具** | 中 | 中 | Sprint 2 前专注"为什么用户需要 App 而不是纸笔"的持续验证 |
| **游戏化方向与工具定位冲突** | 中 | 低 | 创新方向后置到 Sprint 3 之后，仅在验证核心价值后考虑 |
| **市场天花板低** | 高 | 中 | 接受"小而美"的垂直定位，避免与通用工具竞争 |
