# 规划收敛结果

---

## 共识点

1. **核心价值锚定一致**：计数器的核心价值是"快速、准确、轻量"，MVP 阶段必须保持极简主义，不添加任何增加交互负担的功能。

2. **手机原生功能是真实威胁**：iOS 快捷指令、Android Assistant、厂商 Widget 正在系统性替代通用计数器应用，这是所有分析都承认的市场现实。

3. **MVP 应先于完整功能**：所有 Agent 都同意应先完成最小可行产品，用实际市场反馈驱动后续开发，而非预先设计完整功能矩阵。

4. **技术实现本身不复杂**：在"最简形态"定义明确的前提下，计数器应用的技术实现难度确实很低（2/10），但复杂度会随功能扩展急剧上升。

5. **边界条件是产品决策**：计数器为 0 时点击减法如何处理、是否有上下限——这些不是技术问题，而是必须在开发前锁定产品定义。

6. **云同步是架构决策而非功能决策**：同步方案（乐观锁、本地优先等）必须在架构设计阶段确定，而非在 Sprint N 中临时引入。

---

## 关键分歧

### 分歧 1：需求完整性与启动时机的平衡

- **需求重构洞察者**：主张在启动开发前必须明确"谁在用、怎么用、解决什么痛点"，否则核心功能定义不清。
- **颠覆式创新官**：认为产品定义应在验证中收敛，而非在规划阶段穷究；"先搞清楚再开始"会杀死所有创新。
- **规划收敛者**：只需确认 2 个关键约束（目标平台、交付时间节点），其余通过快速迭代验证。

**最终裁决**：采纳规划收敛者的精简框架，但要求在 Sprint 0 中完成基础假设锁定：
- **目标平台**：移动端 iOS/Android（高优先级）或 Web
- **交付时间节点**：明确
- **核心假设文档化**：记录所有未经验证的假设（如"用户需要保存计数历史"），标注为"待验证"，而非"已确认"

---

### 分歧 2：创新方向（生命日志引擎）的定位

- **颠覆式创新官**：生命日志引擎是差异化方向，但需要功能分层——极简计数是默认路径，标签/语音是可选增强层。
- **需求重构洞察者/商业闭环操盘手**：生命日志方向会摧毁计数器"轻量快速"的核心价值，变成四不像产品。
- **工程落地官**：生命日志与极简交互在交互频率、操作负担上存在内在冲突，需要明确是同一产品的不同模式还是两个独立产品线。

**最终裁决**：生命日志方向可以保留在产品路线图中，但必须与 MVP 明确切割：
- **MVP（Sprint 1-3）**：纯计数器，无任何标签、语音、拍照功能
- **Sprint 4+（条件触发）**：仅在 MVP 验证"用户留存率 > 30%"后，才考虑引入可选的标签功能作为付费墙解锁项
- **设计约束**：若引入标签功能，必须是折叠的（点击才展开），不干扰默认计数路径

---

### 分歧 3：商业模型的优先级与设计

- **商业闭环操盘手**： Freemium 订阅制 + B2B 企业版是主路径；ARPU 估算 $2-5/年，付费转化率 2-5%。
- **需求重构洞察者/规划收敛者**：在需求未验证阶段谈商业变现是本末倒置；工具类应用付费意愿偏低是现实约束。
- **工程落地官**（部分质疑）：TAM 计算缺乏数据支撑，"潜在用户"不等于"有效市场"。

**最终裁决**：商业模型应后置至 Product-Market Fit 验证之后，具体调整如下：
- **删除**：Sprint 规划中的所有商业变现相关内容（ARPU、TAM、Freemium 细节）
- **付费墙设计修正**：若未来引入付费功能，付费墙应从"计数器数量限制"改为"数据价值解锁"（历史记录导出、统计图表），因为前者可被多账号绕过
- **转化率修正**：采用更保守的基准——0.5-1.5%（非 2-5%），对应工具类应用的行业现实
- **B2B 方向保留**：作为长期战略选项，在 MVP 验证 C 端后再评估是否切入

---

### 分歧 4：Sprint 规划中边界条件的时机

- **工程落地官**（质疑规划收敛者）：边界条件（最小值限制）应放在 Sprint 1 而非 Sprint 2，因为"计数器为 0 时点击减"是产品决策，决定 UI 逻辑和交互流程，Sprint 1 写好的减法逻辑会在 Sprint 2 返工。
- **颠覆式创新官**（被质疑方）：质疑 Sprint 规划缺少用户故事，认为在没有用户反馈的情况下规划技术任务存在风险。

**最终裁决**：边界条件必须在 Sprint 0 冻结，Sprint 1 开始前锁定产品定义文档：
- **最小值**：0（到达 0 时减法操作无效果，UI 反馈为按钮短暂禁用）
- **最大值**：10,000（到达上限时禁止继续增加）
- **溢出处理**：显示 "9999+"，禁止继续增加
- **交互反馈**：按钮禁用（视觉）而非 toast 提示（减少认知负担）

---

### 分歧 5：用户验证的时机与方法

- **需求重构洞察者**：主张在规划前完成用户验证，回答"谁会用、怎么用"的问题。
- **颠覆式创新官**：颠覆式创新用户往往不知道自己想要什么，需要"快速原型 + 市场验证"而非"充分调研 + 详细规划"。
- **商业闭环操盘手**：Sprint 规划缺少用户获取策略，需要在 Sprint 0 中补充验证计划。

**最终裁决**：采用"轻量验证 + 快速迭代"的混合模型：
- **Sprint 0（1-2 天）**：完成基础竞品分析（App Store 排名前 10 的计数器应用功能拆解）+ 5-10 人用户访谈（核心问题："你上次需要计数是什么时候？怎么解决的？"）
- **Sprint 1-3**：MVP 开发，同步在小范围（100 人）内测
- **Sprint 3 结束**：基于真实用户数据（而非假设）判断功能优先级

---

### 分歧 6：技术风险等级（并发/竞态条件）

- **工程落地官**（质疑商业闭环操盘手）：单用户多端登录场景同样存在竞态条件，云同步作为付费卖点必须早期实现，技术复杂度应上调。
- **规划收敛者**：并发风险列为"低"，理由是"若涉及多用户"。

**最终裁决**：并发风险等级从"低"上调为"中"，架构设计阶段明确同步策略：
- **MVP 阶段**：单设备使用，不支持云同步
- **架构要求**：技术架构必须支持未来的多设备同步（推荐乐观锁 + 本地优先策略）
- **文档声明**：在 MVP 用户协议中明确"当前版本单设备使用，后续版本支持多设备同步"

## 收敛需求

### 产品定位

**计数器 2.0 = 极简计数 + 可验证的成长轨迹**

不是"更好的计数器"，也不是"生命日志引擎"，而是一个**在轻量与深度之间让用户自己选择**的产品。默认路径是"点一下，记一下"，进阶路径是"记录为什么点"。

### 目标用户（修正版）

- **主要用户**：需要快速计数但手机原生工具无法满足的群体
- **典型场景**：健身计数（组数/次数）、习惯打卡（每日目标）、活动签到（一次性统计）
- **明确排除**：原生工具能完美满足的极简场景（如 iOS 快捷指令已覆盖的功能）

### 功能边界（MVP 冻结）

| 功能 | Sprint | 备注 |
|------|--------|------|
| 增/减/重置计数 | Sprint 1 | 核心路径 |
| 计数值显示 | Sprint 1 | - |
| 边界处理（0-10,000） | Sprint 0（产品决策） | 按钮禁用式反馈 |
| 本地状态持久化 | Sprint 2 | 重启后保留计数 |
| 视觉反馈（点击动效） | Sprint 2 | - |
| 基础测试 | Sprint 2 | - |
| 用户体验优化 | Sprint 3 | - |

**明确排除（MVP 阶段）**：
- 语音/拍照标签
- 云同步
- 多计数器管理
- 数据导出/统计图表
- 成就系统/游戏化

### 技术约束（MVP 冻结）

- **目标平台**：移动端（iOS/Android）
- **技术栈**：Flutter 或 React Native（跨平台优先）或原生开发（性能优先）
- **数据存储**：本地存储（localStorage / SQLite）
- **架构要求**：模块化设计，支持未来功能扩展

## 验收标准

| 阶段 | 验收维度 | 指标 |
|------|----------|------|
| **Sprint 1 结束** | 功能验收 | 增/减/重置操作成功率 > 98%；边界处理正确（0 不可减，10,000 不可增） |
| **Sprint 2 结束** | 数据验收 | 重启后计数状态正确保留；无数据丢失 |
| **Sprint 3 结束** | 体验验收 | 用户完成核心操作时间 < 3 秒；Crash rate < 0.1% |
| **MVP 发布后 2 周** | 市场验证 | 下载量 > 500（渠道：TestFlight/Google Play Beta）；7 日留存率 > 20%；若 < 10%，需重新审视产品定位 |
| **MVP 发布后 1 个月** | 增长验证 | 净推荐值（NPS）> 30；自然传播率 > 5%（用户自发推荐/社交分享） |

**退出条件**：
- 若 Sprint 1 结束核心功能仍未稳定 → 暂停项目，重新评估技术方案
- 若 MVP 发布后 1 个月留存率 < 10% → 停止迭代，重新做用户调研

## 风险与注意事项

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| **手机原生功能替代** | 高 | 差异化聚焦于原生工具无法满足的场景（如多组训练计数、活动签到统计）；在产品描述中明确差异化价值 |
| **需求范围蔓延** | 高 | Sprint 1-3 阶段严格执行功能冻结表；任何新增功能必须经过"MVP 验证通过后才考虑"的门槛 |
| **付费转化率低于预期** | 中 | 采用"数据价值解锁"式付费墙（非计数器数量限制）；关注 B2B 企业版作为替代变现路径 |
| **技术债务阻碍扩展** | 中 | Sprint 0 明确架构设计原则（模块化、本地优先支持未来同步）；MVP 代码必须具备可维护性 |
| **用户获取成本高于 LTV** | 中 | MVP 阶段控制推广成本（TestFlight/Beta 测试）；优先验证自然增长而非付费推广 |
| **MVP 与愿景混淆** | 低 | 产品路线图与 Sprint 规划完全分离；路线图标注"基于 MVP 验证结果调整" |
| **并发/多设备同步技术债务** | 中 | 架构设计预留扩展性；MVP 阶段明确单设备使用声明；不将云同步作为核心卖点 |

---

**最终结论**：这是一个**可以做、但必须差异化才能存活**的项目。差异化不在于功能堆砌，而在于**对特定垂直场景的深度满足**。MVP 的目标不是"功能完整的计数器"，而是"验证特定用户群体是否真的需要这个产品"。所有创新和变现的设计，都必须在这个验证结果的基础上展开。
